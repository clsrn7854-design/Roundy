# Roundy 프로젝트 기획서

Oct 30, 2026 · @승

## 한눈에 보기

Roundy(오늘 뛰기 좋은 우리 동네 한 바퀴)는 집 근처에서 원하는 거리의 순환 러닝 코스를 날씨와 대기질을 반영해 추천하는 반응형 웹이다. MVP는 서울 송파구를 대상으로 8주 동안 만들고, 이후 마포구로 넓힌다.

**MVP가 답해야 할 3가지**

1. 실제 길 데이터로 출발지에 돌아오는 순환 코스를 만들 수 있는가
2. 만든 코스가 원하는 거리와 환경 조건(평지, 공원·강변, 화장실)을 만족하는가
3. 날씨와 대기질을 근거로 오늘 뛸지 판단할 수 있는가

AI 검색은 이 셋을 더 편하게 쓰게 하는 부가 기능이다.

**꼭 만들 기능 (P0)**

1. 회원: 이메일 가입과 로그인, 선호 조건(거리, 난이도, 페이스)과 자주 쓰는 출발지(집, 회사) 저장
2. 오늘의 컨디션: 날씨와 미세먼지, 러닝 지수(0\~100점), 실내 운동 권장 경고
3. 코스 추천 (핵심): 출발지와 거리를 정하면 돌아오는 코스를 최대 3개 생성, 공원과 강변 길 우선, 평지와 화장실 조건
4. AI 검색: 자연어를 검색 조건으로 변환, 실제 데이터로만 추천 이유 설명, AI 실패 시 일반 검색으로 대체
5. 코스 상세와 저장: 지도 경로, 거리, 고도차, 예상 시간, 데이터 출처, 즐겨찾기

**시간 되면 (P1)**: 소셜 로그인, 좋은 시간대 추천, 고도 그래프, GPX 내보내기, 두루누비 공식 코스

**이번엔 안 함**: 러닝 기록, 후기, 야간 조명, 송파구 외 지역

| 기술 | 역할 |
| --- | --- |
| Neo4j | 길 그래프, 순환 코스 찾기 |
| PostgreSQL | 회원, 코스, 공원, 화장실, AI 호출 로그(JSONB) |
| Redis | 날씨와 미세먼지 캐시 |
| LangChain | 자연어를 조건으로 변환, 추천 이유 생성 |
| pgvector | MVP 이후 확장 단계에서 의미 검색에 도입 |
| Claude Haiku 5.5 | LLM (6주차에 GPT-6 Luna와 비교해 확정) |
| 카카오맵 | 지도 표시(JavaScript SDK)와 장소 검색(로컬 REST API) |

**정할 것**: 모두 결정됨 (내용은 '결정 사항' 참고)

## 프로젝트 개요

흩어진 공공데이터를 모아 조건에 맞는 코스 추천부터 추천 이유 설명까지 한 서비스에서 처리하는 것이 목표다.

**배경과 문제**

- 러너는 뛰기 전에 날씨 앱, 미세먼지 앱, 지도 앱을 따로 확인해야 한다.
- "5km 정도에 평지 위주로, 출발한 곳으로 돌아오는 코스"처럼 조건에 맞는 코스를 찾기 어렵다.
- 두루누비 같은 공식 코스는 장거리 여행길 위주라, 동네 공원이나 강변에서 짧게 뛰는 코스는 거의 없다.
- 화장실 같은 편의 정보도 한 곳에 모여 있지 않다.

**목표**

- 집 근처 출발지에서 목표 거리의 순환 코스를 OpenStreetMap 길 그래프로 직접 생성한다.
- 날씨와 대기질로 오늘 뛰기 좋은지 판단해준다.
- 추천 이유를 실제 데이터 값으로 설명한다.

**대상 지역**: MVP는 서울 송파구(석촌호수, 올림픽공원, 잠실한강공원, 탄천, 성내천)로 시작하고, 확장 단계에서 마포구로 넓힌다. 송파구는 호수, 공원, 강변, 하천길이 한 구 안에 모두 있고 대부분 평지라 첫 경로 탐색에 적합하다. 데이터 용량과 무료 DB 제한 때문에 지역을 좁힌다.

**플랫폼**: 반응형 웹 (PC는 3단 레이아웃, 모바일은 화면 전환형)

**문제와 해결**

| 문제 | Roundy의 해결 | 사용자 가치 |
| --- | --- | --- |
| 날씨, 미세먼지, 지도, 편의시설을 앱마다 따로 확인 | 러닝 지수, 순환 코스, 주변 화장실을 한 화면에 제공 | 오늘 어디서 뛸지 빠르게 결정 |
| 거리, 평지, 순환 같은 조건에 맞는 코스를 찾기 어려움 | 출발지와 거리만 정하면 길 그래프로 순환 코스 생성 | 코스를 찾는 시간과 수고 감소 |
| 공식 코스는 장거리 위주라 동네 코스 정보가 부족 | 공원과 강변 길을 우선하는 동네 코스 생성 | 집·회사 근처에서 바로 출발 |

**성공 기준**: 목표값이 없는 항목은 1주차 데이터 검증과 순환 코스 시제품 결과를 보고 정한다.

| 항목 | 측정 방법 | 목표값 |
| --- | --- | --- |
| 코스 생성 성공률 | 유효한 요청 중 코스를 1개 이상 만든 비율 | 1주차 후 설정 |
| 거리 정확도 | 목표 거리 대비 실제 경로 거리 오차 | ±10% 이내 (FR-C3) |
| 출발점 복귀 | 경로 끝점과 출발점 사이 거리 | 1주차 후 설정 |
| 코스 다양성 | 추천 3개 사이의 공통 구간 비율 | 1주차 후 설정 |
| 응답 속도 | 코스 생성 API 응답 시간 | 3초 이내 |
| 데이터 신뢰성 | 화면마다 출처와 기준 시각을 표시하는지 | 모든 화면 |

## 타깃 사용자

핵심 사용자는 평일 저녁 집이나 회사 근처에서 5km 내외를 뛰는 퇴근 후 러너다. 주말 장거리 러너는 송파구 하나로는 10\~20km 코스를 다양하게 만들기 어려워, 지역을 넓히고 최적 시간대·공식 코스(P1)를 붙이는 확장 단계의 타깃으로 둔다.

| 페르소나 | 특징 | 필요한 것 |
| --- | --- | --- |
| 퇴근 후 러너 (20\~30대 직장인) | 평일 저녁 5km 내외, 집이나 회사 근처 출발 | 출발지로 돌아오는 짧은 코스 |
| 입문 러너 | 러닝 3\~6개월 차, 무릎 부담이 걱정됨 | 평지 위주 코스, 화장실과 쉴 곳 정보 |
| 주말 장거리 러너 (확장 단계 타깃) | 하프나 풀코스 준비, 10\~20km | 새로운 코스 탐색, 날씨에 따른 최적 시간대 |

## 기능 요구사항

P0는 MVP에 반드시 넣고, P1은 시간이 되면 넣는다. 핵심은 C 그룹의 순환 코스 생성이다.

| ID | 기능 | 우선순위 | 완료 기준 |
| --- | --- | --- | --- |
| **A. 회원** |  |  |  |
| FR-A1 | 회원가입과 로그인 | P0 | 이메일 가입과 로그인(이메일 중복 확인, 비밀번호 해시 저장), JWT 발급, 로그아웃(프론트에서 토큰 삭제) |
| FR-A2 | 소셜 로그인 | P1 | 카카오 또는 구글 로그인 |
| FR-A3 | 선호 조건 설정 | P0 | 기본 거리, 난이도, 평소 페이스(예: 6분/km) 저장과 수정. 출발지는 저장된 장소(FR-C8)로 관리 |
| FR-A4 | 현재 위치 사용 (브라우저 허용) | P1 | 별도 동의 화면 없이 브라우저 기본 허용 창 사용, 좌표는 추천 요청에만 쓰고 저장하지 않음 |
| FR-A5 | 회원 탈퇴 | P1 | 탈퇴하면 계정, 저장된 장소, 즐겨찾기, 검색 기록을 함께 삭제 |
| FR-A6 | 비밀번호 재설정 | P1 | 메일 인증으로 재설정 (메일 발송 기능이 필요해 MVP 제외) |
| **B. 러닝 컨디션** |  |  |  |
| FR-B1 | 현재 날씨와 대기질 조회 | P0 | 출발지 기준 기온, 강수, 풍속, 미세먼지 표시 |
| FR-B2 | 러닝 지수 계산 | P0 | 0\~100점과 등급(좋음/보통/주의/실내 권장), 계산 근거 값 함께 제공 |
| FR-B3 | 실내 운동 권장 | P0 | 비나 눈, 미세먼지 매우 나쁨, 폭염·한파 특보일 때 경고 표시 |
| FR-B4 | 가장 좋은 시간대 추천 | P1 | 오늘 남은 시간 중 지수가 가장 높은 시간대 표시 |
| FR-B5 | 데이터 기준 시각 표시 | P0 | "기상청 19:00 기준" 같은 기준 시각 표시 |
| FR-B6 | 데이터 신선도 표시 | P0 | 외부 API가 실패하면 마지막 정상 값과 기준 시각을 함께 표시, 오래된 값은 오래됐다고 표시, 캐시도 없으면 조회 실패 안내 (비기능 요구사항의 신선도 정책) |
| **C. 코스 검색과 추천** |  |  |  |
| FR-C1 | 출발지 설정 | P0 | 장소 이름·주소 검색이 기본(예: "석촌호수"), 검색 결과 핀을 끌어서 위치 조정, 지도 클릭으로도 설정, 저장된 장소(집, 회사)는 한 번 클릭으로 선택, 현재 위치는 보조 |
| FR-C2 | 조건 필터 | P0 | 거리(3/5/10km 또는 직접 입력), 평지 여부, 화장실 포함 여부 |
| FR-C3 | 순환 코스 생성 | P0 | 출발지로 돌아오는 코스를 목표 거리 ±10% 안에서 최대 3개 생성 |
| FR-C4 | 공원/강변 우선 경로 | P0 | 공원과 강변 길에 가중치를 줘서 큰 도로 옆 인도 비율을 줄임 |
| FR-C5 | 코스 점수화와 정렬 | P0 | 필수 조건을 통과한 후보만 거리 일치도, 누적 상승 고도, 공원·강변 비율, 화장실(2곳 이상은 가점 상한)로 점수 계산 후 정렬 |
| FR-C6 | 공식 코스 목록 | P1 | 두루누비 코스를 지역별로 조회 |
| FR-C7 | 생성 실패 처리 | P0 | 조건에 맞는 코스가 없으면 조건 완화 제안 (예: "4km 코스는 있어요") |
| FR-C8 | 자주 쓰는 출발지 저장 | P0 | 집, 회사 등 이름을 붙여 최대 5곳 저장, 수정과 삭제 가능, 검색창에서 바로 선택 |
| FR-C9 | 출발지 설정 방식 기록 | P1 | 검색, 지도 클릭, 핀 조정, 저장된 장소, 현재 위치 중 어느 방식을 썼는지 기록해 화면 개선 근거로 활용 |
| FR-C10 | 코스 중복 제거 | P0 | 추천 후보끼리 공통 구간 비율이 기준을 넘으면 점수가 낮은 쪽을 제외 (기준값은 테스트 후 결정) |
| FR-C11 | 코스 유효성 검사 | P0 | 출발점 복귀, 끊긴 구간 없음, 보행 가능한 길만 사용, 거리 ±10%, 왕복 비율 기준 이하, 사용자가 고른 조건(평지, 화장실), 고도 누락 구간 처리를 통과한 코스만 추천 |
| **D. AI 검색** |  |  |  |
| FR-D1 | 자연어를 조건으로 변환 | P0 | "퇴근 후 5km 평지 화장실"을 거리, 평지, 화장실 조건(JSON)으로 변환 |
| FR-D2 | 변환 결과 확인 | P0 | 변환된 조건을 태그로 보여주고 사용자가 수정 가능 |
| FR-D3 | 추천 이유 생성 | P0 | 실제 데이터 값만 사용해 코스별 1\~2문장 설명 |
| FR-D4 | AI 장애 대비 | P0 | LLM 호출이 실패하면 일반 필터 검색으로 대신 처리 |
| **E. 코스 상세** |  |  |  |
| FR-E1 | 지도 경로 표시 | P0 | 경로 선, 출발점, 화장실 마커, 공원 영역 |
| FR-E2 | 코스 요약 정보 | P0 | 거리, 고도차, 예상 소요 시간(사용자 페이스 기준, 로그인하지 않았으면 기본 페이스 6분 30초/km) |
| FR-E3 | 고도 그래프 | P1 | 거리에 따른 고도 변화 그래프 |
| FR-E4 | 데이터 출처 표시 | P0 | 사용한 데이터 출처와 OSM 저작권 표기 |
| FR-E5 | GPX 내보내기 | P1 | 경로를 GPX 파일로 다운로드 |
| **F. 즐겨찾기** |  |  |  |
| FR-F1 | 코스 저장 | P0 | 생성된 코스를 이름 붙여 저장, 같은 코스는 중복 저장되지 않음 |
| FR-F2 | 저장 목록 조회 | P0 | 저장한 코스 목록과 오늘의 러닝 지수 함께 표시 |
| FR-F3 | 저장 삭제 | P0 | 즐겨찾기에서 삭제 |
| **G. 데이터 수집과 관리 (내부)** |  |  |  |
| FR-G1 | 좌표 통일 | P0 | 모든 데이터를 WGS84로 변환, 기상청 격자와 에어코리아 TM 변환 모듈 |
| FR-G2 | OSM 적재 | P0 | 대상 지역의 보행 가능 길만 추출해 Neo4j에 적재 |
| FR-G3 | 고도 매핑 | P0 | rasterio로 그래프 지점마다 고도 값 부여, 경로 고도는 튀는 값을 보정하고 1\~2m 미만 변화는 고도차에서 제외 |
| FR-G4 | 공공데이터 적재 | P0 | 공원, 화장실 데이터 적재와 근접 관계 생성 |
| FR-G5 | 데이터 품질 리포트 | P1 | 지역별 데이터 개수, 기준일, 누락 항목 확인 스크립트 |
| FR-G6 | 두루누비 정기 수집 | P1 | 주 1회 자동 수집 |

## MVP 제외 범위와 사용자 흐름

러닝 기록, 후기, 야간 조명은 데이터가 쌓이거나 품질이 확보된 뒤 다음 버전에서 다룬다.

**MVP에서 제외**

- 러닝 기록과 신발 관리
- 코스 후기와 후기 의미 검색 (후기 데이터가 쌓여야 의미가 있음)
- 야간 조명 정보 (보안등 데이터 품질 문제)
- 소셜 기능, 실시간 GPS 트래킹, 웨어러블 직접 연동
- 송파구 외 지역 (마포구는 확장 단계에서 추가)

**사용자 흐름**

1. 메인에서 저장된 장소(집, 회사)를 고르거나 주소 검색·지도 클릭으로 출발지를 정한다. 현재 위치도 쓸 수 있다.
2. 오늘의 러닝 컨디션(기상청, 에어코리아)을 확인한다.
3. 자연어 또는 필터로 조건을 입력한다. LLM이 자연어를 검색 조건(JSON)으로 바꾼다.
4. 점수순으로 정렬된 추천 코스 3개와 추천 이유를 본다.
5. 코스 상세에서 지도 경로, 편의시설, 예상 시간을 확인한다.
6. 마음에 드는 코스를 즐겨찾기에 저장한다.

## 기술 스택과 아키텍처

이미 배운 React와 FastAPI를 중심에 두고, 주제에 필요한 DB만 붙인다. Django 대신 FastAPI를 쓴다.

| 구분 | 기술 | 선정 이유 |
| --- | --- | --- |
| 프론트엔드 | React (여유가 되면 Next.js) | 이미 학습한 기술, 지도 SDK 연동 자료가 많음 |
| 백엔드 | FastAPI | 이미 학습한 기술, 비동기로 여러 외부 API를 동시에 호출하기 좋고 LLM 응답 처리에 적합 |
| 메인 DB | PostgreSQL | 회원, 코스, 공원 등 정형 데이터. SQL은 MariaDB와 거의 같고 PostGIS로 위치 검색 확장 가능 |
| 벡터 검색 | pgvector (확장 단계) | MVP 이후 후기와 코스 설명 의미 검색에 도입. 별도 벡터 DB 없이 같은 DB에서 처리 |
| 그래프 DB | Neo4j | 보행로 네트워크를 그래프로 저장해 경로 탐색과 순환 코스 생성 |
| 캐시 | Redis | MVP는 날씨·대기질·특보 API 응답만 캐싱 (호출 제한 대응). 러닝 지수·장소 검색·LLM 캐시는 성능을 측정한 뒤 추가 |
| 로그 | PostgreSQL JSONB 컬럼 | LLM 호출 로그. 구조가 자주 바뀌어도 JSONB로 저장할 수 있어 DB를 늘리지 않음 |
| AI | LangChain + Claude API (Haiku 5.5로 시작) | 자연어를 검색 조건으로 변환, 추천 이유 생성 |
| 인프라 | Docker, AWS EC2, GitHub Actions | 환경 일관성, 배포 자동화 |
| 지도 | 카카오맵 JavaScript SDK + 카카오 로컬 REST API | 한국 지도 품질과 장소 이름 검색을 한 곳에서 해결, 무료 사용량이 넉넉함. 검색은 REST API 키 보호와 기록·캐싱을 위해 백엔드에서 호출 |

&#91;embedded content: 시스템 아키텍처 · FastAPI 서버와 DB 3개\]

브라우저는 FastAPI만 호출하고, FastAPI가 외부 API 호출과 DB 3개 접근을 모두 맡는다.

**기술 결정 (2026-10-30)**

- &#91;검증 후 확정, 1주차\] Neo4j 유지: 길, 공원, 화장실의 관계를 함께 탐색하는 경로 쿼리를 쓰기 쉽다. 1주차에 송파구 일부로 순환 코스 시제품을 만들어 보고, 적재·AuraDB 용량·경로 생성 중 하나라도 막히면 PostGIS + pgRouting으로 바꾼다. 비교 결과는 면접 자료로 남긴다.
- &#91;확정\] LangChain 유지: 구조화된 출력과 모델 교체를 한 인터페이스로 처리하고, AX 과정에서 배운 내용을 활용한다. 6주차 Claude·GPT 비교도 모델 설정만 바꿔 진행할 수 있다.
- &#91;확정\] pgvector는 확장 단계: MVP에는 의미 검색할 텍스트가 거의 없어 후기 기능과 함께 도입한다.
- &#91;확정\] MongoDB 제외: LLM 로그는 PostgreSQL JSONB 컬럼에 저장해 운영할 DB를 3개로 줄인다.

* &#91;검증 후 확정, 6주차\] LLM은 Claude Haiku 5.5(claude-haiku-5-5)로 시작: 조건 변환과 짧은 설명은 단순한 작업이고, 코스 생성 3초 목표에 빠른 응답이 필요하다. 6주차에 테스트 문장 20개(애매한 표현 포함)로 가격이 같은 OpenAI GPT-6 Luna(gpt-6-luna, 둘 다 100만 토큰당 입력 $0.10 / 출력 $0.50)와 정확도·응답 시간·비용을 비교해 확정한다. 두 모델 모두 애매한 문장을 자주 놓치면 조건 변환만 큰 모델을 쓴다. 비교 결과는 포트폴리오의 기술 선택 근거로 남긴다.

- &#91;검증 후 확정, 1주차\] 고도는 Copernicus DEM으로 시작: 신청 없이 바로 받을 수 있고, 같은 30m 해상도에서 보통 SRTM보다 정확하다고 평가된다. 1주차에 몽촌토성 언덕과 석촌호수·한강변 평지를 비교해 검증하고, 결과가 나쁘면 국토지리정보원 5m 데이터로 바꾼다.

모델 ID와 가격은 2026-10-30에 공식 가격표에서 확인했다: [Claude 가격](https://platform.claude.com/docs/en/about-claude/pricing), [OpenAI 가격](https://developers.openai.com/api/docs/pricing). 비교하기 전에 다시 확인한다.

**배포 구조**: 프리티어 EC2(메모리 약 1GB)에는 FastAPI만 올리고, DB는 각자의 무료 클라우드 플랜으로 분리한다. 한 서버에 DB 3개를 모두 올리면 메모리가 부족하다.

| DB | 무료 옵션 |
| --- | --- |
| PostgreSQL | AWS RDS 프리티어 또는 Supabase (pgvector 지원) |
| Neo4j | Neo4j AuraDB Free |
| Redis | Redis Cloud 또는 Upstash 무료 플랜 |

각 무료 플랜의 용량 제한은 가입할 때 확인한다. 특히 AuraDB Free는 노드와 관계 수 제한이 있어 대상 지역을 좁혀야 한다. 로컬에서는 Docker Compose로 전체 환경을 띄운다.

## 데이터 모델

정형 데이터는 PostgreSQL, 길의 연결 관계는 Neo4j, 자주 바뀌는 외부 값은 Redis, LLM 로그는 PostgreSQL JSONB 컬럼에 둔다.

**PostgreSQL**

```
users              (id, email UNIQUE, password_hash, nickname, pref_distance_km, pref_difficulty, pace_sec_per_km, created_at)
saved_places       (id, user_id, label, address, location, created_at)
courses            (id, user_id, source, name, start_location, distance_km, elevation_gain_m, geometry, generation_conditions JSONB, score, created_at)
course_parks       (course_id, park_id)
course_facilities  (course_id, facility_id)
parks              (id, name, location, area_m2, source, base_date)
facilities         (id, type, location, open_hours, source, base_date)
favorites          (id, user_id, course_id, name, created_at, UNIQUE(user_id, course_id))
llm_logs           (id, model, request_masked, parsed_conditions JSONB, response JSONB, success, error_code, tokens, latency_ms, created_at)
search_logs        (id, user_id, origin_method, conditions JSONB, created_at)      (P1)
```

`search_logs.origin_method`는 출발지를 정한 방식(search, map\_click, pin\_adjust, saved\_place, current\_location)이며, 정확한 좌표는 저장하지 않는다.

**관계**

- users 1:N saved\_places, favorites, courses(코스를 생성한 사용자)
- courses 1:N favorites
- courses N:M parks (course\_parks), courses N:M facilities (course\_facilities)

**코스 저장 정책**: 생성된 코스는 모두 저장해 상세 화면 주소(`/courses/{id}`)와 성공률 같은 지표에 쓴다. 즐겨찾기하지 않은 코스는 7일이 지나면 삭제한다.

**좌표 규칙**: 내부 표준은 WGS84, 좌표 순서는 GeoJSON과 같은 `[경도, 위도]`다. 카카오 지도의 `LatLng(위도, 경도)` 변환은 프론트엔드 유틸 한 곳에서만 한다. 기상청 격자(nx, ny)와 에어코리아 TM 변환은 백엔드의 좌표 변환 모듈이 따로 맡고, 위치를 아는 테스트 좌표로 검증한다.

**Neo4j**

```
(:Node {id, lat, lng, elevation})                       교차로나 경로 지점
(:Node)-[:ROAD {length_m, type, in_park, riverside}]->(:Node)   보행 가능한 길
(:Facility)-[:NEAR]->(:Node)                           편의시설과 가까운 지점
(:Park)-[:CONTAINS]->(:Node)                           공원 안의 지점
```

**Redis**

```
weather:{nx}:{ny}         TTL 1시간    격자별 날씨
air:{station}             TTL 1시간    측정소별 대기질
alert:{area}              TTL 30분     기상특보
*:last:*                  TTL 없음    마지막 정상 값 (장애 대비)
```

러닝 지수, 장소 검색, LLM 결과 캐시는 개선 전 응답 시간을 측정한 뒤 추가한다.

**pgvector (확장 단계)**

```
course_reviews   (id, user_id, course_id, content, embedding vector)   후기 의미 검색
courses.embedding                                                     코스와 공원 설명 의미 검색
```

## 핵심 로직

코스는 그래프 탐색으로 만들고, LLM은 조건 변환과 설명만 맡는다.

**러닝 지수 (0\~100점)**

```latex
I = w_T S_T + w_A S_A + w_R S_R + w_W S_W, \quad w_T + w_A + w_R + w_W = 1
```

S\_T, S\_A, S\_R, S\_W는 기온, 대기질, 강수, 바람을 각각 0\~100점으로 바꾼 점수다. 원본 값(℃, μg/m³, m/s)을 그대로 더하지 않는다. 아래 구간과 가중치는 자체 기준의 첫 안이고, 테스트와 사용자 피드백으로 조정한다.

| 항목 | 100점 | 중간 | 0점 | 가중치(초안) |
| --- | --- | --- | --- | --- |
| 기온 | 8\~15℃ | 구간에서 멀어질수록 감점 | -5℃ 이하 또는 30℃ 이상 | 0.35 |
| 대기질 (PM10·PM2.5 중 나쁜 등급) | 좋음 | 보통 70, 나쁨 30 | 매우 나쁨 | 0.35 |
| 강수 | 강수 없음, 확률 30% 미만 | 확률 30\~60%면 50 | 비나 눈이 오는 중 | 0.2 |
| 바람 | 4m/s 미만 | 4\~8m/s면 60 | 8m/s 이상 | 0.1 |

**판단 순서**: 점수가 낮다는 이유만으로 실내 운동을 권하지 않는다. 위험 조건을 먼저 검사하고, 해당하면 점수를 내지 않는다.

```
if 강수_중 or 미세먼지_매우_나쁨 or 폭염_한파_특보:
    상태 = "실내 운동 권장"      # 점수는 계산하지 않음
else:
    점수 = 러닝_지수_계산()
    등급 = 점수_구간으로_등급_결정(점수)
```

- 등급: 80점 이상 좋음, 60\~79점 보통, 40\~59점 주의, 40점 미만 실내 권장
- 기온만으로는 위험 조건으로 보지 않는다. 30℃ 이상이면 기온 점수 0점으로 반영되고, 체감온도와 습도는 확장 단계에서 검토한다.
- 데이터가 없는 항목은 계산에서 빼고, 남은 가중치를 합이 1이 되도록 다시 나눈다. 화면에는 "일부 데이터 없음"을 표시하고, 기온과 대기질이 모두 없으면 점수를 내지 않는다.
- 러닝 지수는 의학적·공식 안전 기준이 아니라 서비스의 참고 지표라고 화면과 README에 밝힌다. 구간과 가중치의 근거(참고 자료 또는 자체 기준)도 README에 적는다.

**계산 예시** (단위 테스트로 고정): 위험 조건에 해당하지 않는 더운 날

| 항목 | 입력 | 점수 | 가중치 | 반영 |
| --- | --- | --- | --- | --- |
| 기온 | 30℃ | 0 | 0.35 | 0 |
| 대기질 | PM2.5 50μg/m³ (나쁨) | 30 | 0.35 | 10.5 |
| 강수 | 0mm, 확률 30% 미만 | 100 | 0.2 | 20 |
| 바람 | 2m/s | 100 | 0.1 | 10 |
| 합계 |  |  |  | 40.5점, 주의 |

같은 50이라도 PM10이면 등급이 보통(70점)이라 54.5점이 된다. 그래서 대기질은 PM10과 PM2.5 중 나쁜 등급을 쓴다.

**코스 점수**: 아래 순환 코스 생성의 필수 조건을 통과한 후보만 점수를 매긴다. 보행 가능 여부 같은 안전 조건은 점수로 보상하지 않는다. 항목마다 0\~100점으로 바꾼 뒤 가중치를 곱해 더하고, 구간과 가중치는 초안이다.

| 항목 | 계산 방식 | 가중치(초안) |
| --- | --- | --- |
| 거리 일치도 | 오차 0%면 100점, 10%면 0점 | 0.3 |
| 공원·강변 비율 | 코스 중 공원·강변 길 비율(%)을 그대로 점수로 | 0.3 |
| 누적 상승 고도 | 낮을수록 높은 점수 (구간은 1주차 고도 검증 후) | 0.2 |
| 화장실 | 0곳 0점, 1곳 70점, 2곳 이상 100점 (가점 상한) | 0.2 |

**순환 코스 생성**

1. 출발지와 가장 가까운 그래프 지점을 찾는다.
2. 경유지 후보를 고른다. 출발지에서 직선거리로 목표 거리의 약 1/4\~1/3 범위에 있고, 끊기지 않은 가장 큰 길 네트워크에 속한 지점만 후보로 하고, 공원·강변 길에 붙은 지점을 우선한다. 방향은 서로 다르게(예: 0°, 120°, 240°) 나눠 비슷한 코스만 나오는 것을 막는다.
3. 방향마다 출발지 → 경유1 → 경유2 → 출발지를 가중치 최단 경로로 잇는다. 같은 길을 왕복하지 않도록 이미 지난 구간에는 감점을 준다.
4. 거리 보정: 공원·강변 가중치 때문에 경로가 목표보다 길거나 짧아질 수 있다. 실제 거리가 목표 ±10%를 벗어나면 경유지 반경에 "목표 거리 ÷ 실제 거리"를 곱해 다시 탐색한다. 최대 3회.
5. 필수 조건 검사(FR-C11): 출발점 복귀, 끊긴 구간 없음, 거리 ±10%, 왕복 비율 기준 이하, 사용자가 고른 조건(평지를 고르면 누적 상승 고도 상한, 화장실 포함을 고르면 1곳 이상). 고도가 빠진 지점은 앞뒤 값으로 채우고, 빠진 비율이 높으면 고도차를 "추정"으로 표시한다.
6. 다양성 검사(FR-C10): 코스 간 중복률이 기준을 넘으면 점수가 낮은 쪽을 뺀다.
7. 점수가 높은 순서로 최대 3개를 추천한다. 후보가 모자라면 경유지를 바꿔 다시 탐색하고, 그래도 없으면 조건 완화를 제안한다(FR-C7).

**중복 계산**: 기준값은 1주차 시제품으로 정한다. 초기값 예시는 코스 간 중복률 50%, 왕복 비율 20%다.

```latex
\text{코스 간 중복률} = \frac{\text{공통 길 길이}}{\min(\text{코스 A 길이}, \text{코스 B 길이})} \times 100
```

```latex
\text{왕복 비율} = \frac{\text{두 번 지나는 길 길이}}{\text{코스 전체 길이}} \times 100
```

**속도**: 유효한 코스 3개가 나오면 탐색을 멈추고, 방향별 탐색은 병렬로 실행한다. 공원·강변 여부와 길 네트워크 연결 여부는 데이터를 적재할 때 미리 계산해 둔다. 보정 반복을 포함한 생성 시간은 1주차 시제품에서 측정한다.

**길 가중치**: 공원과 강변 길은 가산점, 큰 도로 옆 인도와 횡단보도가 많은 구간은 감점을 준다. 그대로 최단 경로를 찾으면 차도 옆 인도로만 도는 코스가 나오기 때문이다. 한강 산책로는 나들목 연결을 확인해야 한다.

**LLM의 역할과 안전장치**

- LLM은 코스를 만들지 않는다. 자연어를 조건(JSON)으로 바꾸고, DB에서 찾은 결과를 설명하는 역할만 한다.
- 구조화된 출력(Pydantic 스키마)으로 조건 형식을 고정하고, 스키마에 맞지 않는 응답은 쓰지 않는다.
- 설명에는 실제 데이터 값(미세먼지 수치, 화장실 개수 등)만 쓰도록 프롬프트에 근거 데이터를 함께 넣는다.
- 설명 속 숫자는 백엔드에서 원본 데이터와 대조하고, 맞지 않으면 설명 대신 기본 문구를 쓴다.
- 근거 데이터가 부족하면 설명을 지어내지 않고 생략한다.
- LLM 호출이 실패하면 일반 필터 검색으로 대신 처리한다.

## 리스크와 사전 확인 사항

가장 큰 리스크는 고도 데이터, 배포 메모리, 좌표 체계 3가지다. 1주차에 실제 API 응답을 받아보면 대부분 드러난다.

| 중요도 | 리스크 | 대응 |
| --- | --- | --- |
| 높음 | 순환 코스 생성이 안 되면 핵심 기능이 성립하지 않음 | 1주차에 송파구 일부로 시제품(Neo4j)을 만들어 검증, 적재·AuraDB 용량·경로 생성 중 하나라도 막히면 PostGIS + pgRouting으로 전환 |
| 높음 | 평지 조건을 MVP에 넣었는데 OSM에는 고도 정보가 거의 없음 | 고도 데이터(Copernicus DEM)를 MVP에 포함, 안 되면 "공원/강변 위주" 조건으로 대체 |
| 높음 | 프리티어 EC2 하나에 DB 3개를 올리면 메모리 부족 | EC2에는 FastAPI만, DB는 무료 클라우드 플랜으로 분리 |
| 높음 | 공공데이터마다 좌표 체계가 다름 (기상청 격자 nx/ny, 에어코리아 TM, 지자체 데이터 제각각) | `pyproj`로 WGS84 통일 모듈을 먼저 구현 |
| 중간 | 순환 코스가 차도 옆 인도로만 도는 등 품질이 낮을 수 있음 | 길 종류별 가중치, 한강 나들목 연결 확인 |
| 중간 | 화장실·보안등 데이터 품질과 기준일이 지자체마다 다름 | 품질 확인 스크립트, 화면에 데이터 기준일 표시, 야간 조명은 MVP 제외 |
| 중간 | 현재 날씨와 예보가 다름 (단기예보는 하루 8번 발표되는 예측값) | 현재 값은 초단기실황 API, 특보는 기상특보 API 사용 |
| 중간 | 러닝 지수 기준에 공식 표준이 없음 | 참고 자료를 README에 기록하거나 자체 기준임을 명시 |
| 중간 | 두루누비 API에 경로 좌표가 없을 수 있음 | OSM 경로와 매칭하거나 서울 열린데이터광장 둘레길 데이터로 보완 |
| 중간 | 외부 API 호출 제한과 장애 | Redis 캐싱, 장애 시 마지막 성공 값 사용 |
| 중간 | OSM으로 만든 경로가 카카오 지도에 없는 산책로를 지나 지도와 어긋날 수 있음 | 1주차에 송파구 공원 경로를 카카오 지도에 그려 확인, 많이 어긋나면 지도는 Leaflet(OSM)으로 바꾸고 검색만 카카오 API 사용 (이용약관 먼저 확인) |
| 중간 | 위성 고도 데이터에 건물이나 나무 높이가 섞여 평지가 오르막처럼 계산될 수 있음 | 경로 고도 보정(튀는 값 평균화, 1\~2m 미만 무시), 1주차에 몽촌토성과 평지 구간으로 검증, 나쁘면 국토지리정보원 5m 데이터로 교체 |
| 낮음 | 위치 정보는 개인위치정보에 해당 | 현재 위치 좌표는 저장하지 않음, 저장된 장소는 사용자가 직접 등록하고 삭제 가능 |
| 낮음 | API 키 유출 | 처음부터 `.env`와 `.gitignore` 설정 |
| 낮음 | LLM 비용과 응답 지연 | 같은 요청 캐싱, 가벼운 모델 사용 |
| 낮음 | AWS 비용 | 프리티어 범위 사용, 결제 알림 설정 |

## 개발 원칙과 Claude Code 설정

P0를 끝내기 전에는 P1을 만들지 않고, 이해하지 못한 코드는 넣지 않는다. 아래 두 파일 초안은 프로젝트 폴더를 만든 뒤 `/init`으로 생성한 `CLAUDE.md`에 합치고, `.claude/settings.json`은 직접 만든다.

**개발하면서 주의할 것**

- P0가 끝나기 전에 P1을 만들지 않는다. 5주차가 밀리면 순환 코스를 1개 생성으로 줄이고 배포 일정을 지킨다.
- 크롤링은 하지 않는다. 기획서에 적은 API와 공개 데이터만 쓴다.
- 외부 API를 반복문에서 마구 호출하지 않는다. 개발 중에는 응답을 파일로 저장해 재사용한다.
- OSM과 고도 원본 파일은 git에 올리지 않고 다운로드 스크립트만 올린다.
- `.env`는 첫 커밋 전에 `.gitignore`에 넣는다. 한 번 올라간 키는 새로 발급해야 한다.
- 개선 작업 전에 "개선 전" 수치를 먼저 측정한다.
- 면접에서 설명할 수 없는 코드는 넣지 않는다.

**Claude Code 작업 방식**

| 원칙 | 이유 |
| --- | --- |
| 작게 요청하기 (예: "FR-B2 러닝 지수 계산만") | 한 번에 많이 만들면 검토도 이해도 어렵다 |
| 큰 작업은 계획 먼저 (plan mode) | 코드보다 설계를 먼저 확인한다 |
| 변경 사항(diff)은 직접 읽고 승인 | 무엇이 바뀌었는지 모르고 넘어가지 않는다 |
| 모르는 코드는 설명 요청 | 이해한 뒤에 다음으로 넘어간다 |
| 커밋은 직접 확인 후에 | 기능 단위로 작게 커밋해 기록을 깔끔하게 남긴다 |

**막아둘 것**

| 막을 것 | 이유 | 막는 곳 |
| --- | --- | --- |
| `.env` 파일 읽기 | API 키가 대화에 노출되지 않게 | settings.json |
| `git push --force`, `git reset --hard` | 작업 기록이 사라질 수 있음 | settings.json |
| `rm -rf`, `docker system prune` | 데이터와 DB 볼륨이 지워질 수 있음 | settings.json |
| 실제 LLM API를 반복 호출하는 테스트 | 비용 발생, 테스트는 mock으로 | CLAUDE.md |
| 묻지 않고 새 라이브러리 설치 | 기술 스택이 몰래 늘어나지 않게 | CLAUDE.md |
| DB 데이터 삭제나 스키마 변경 | 적재한 데이터를 다시 만들기 번거로움 | CLAUDE.md |

`CLAUDE.md`는 부탁이라 지켜지지 않을 수도 있고, `settings.json`의 deny는 실행을 실제로 막는다. 꼭 막아야 하는 것은 settings.json에 둔다.

**CLAUDE.md에 합칠 내용 (초안)**

```markdown
# Roundy
- 기획서의 P0 기능만 구현한다. P1은 요청할 때만.
- 새 라이브러리 설치, DB 스키마 변경, 데이터 삭제 전에는 반드시 먼저 묻는다.
- 외부 API와 LLM은 테스트에서 mock으로 대체한다.
- 코드를 작성한 뒤 핵심 로직을 짧게 설명한다.
- 커밋은 사용자가 요청할 때만 한다.
```

**.claude/settings.json 초안**

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Bash(git push --force:*)",
      "Bash(git reset --hard:*)",
      "Bash(rm -rf:*)",
      "Bash(docker system prune:*)"
    ]
  }
}
```

## 포트폴리오 준비

포트폴리오는 프로젝트가 끝난 뒤 몰아서 만들지 않고, 개발하면서 바로 기록을 쌓는다.

**준비할 4가지**

| 형태 | 용도 | 도구 |
| --- | --- | --- |
| 이력서 (1\~2장) | 서류 첫 관문, 프로젝트는 요약만 | 원티드 이력서, 노션, PDF |
| 포트폴리오 문서 | 프로젝트를 자세히 설명 | 노션 + 제출용 PDF (보통 10\~20MB 제한) |
| GitHub | 코드와 README 확인용 | 프로젝트 레포지토리 + 프로필 README |
| 기술 블로그 | 트러블슈팅과 학습 과정 기록 | Velog, Tistory |

**프로젝트 소개 구성**

1. 한 줄 소개 + 대표 이미지(또는 시연 GIF)
2. 기간, 인원, 내 역할
3. 링크: 배포 URL, GitHub, 시연 영상, API 문서(Swagger)
4. 기획 배경: 어떤 문제를 왜 풀었나
5. 주요 기능 3\~5개 (스크린샷과 함께)
6. 기술 스택 + 선정 이유
7. 시스템 아키텍처 다이어그램
8. 트러블슈팅 2\~3개 (가장 중요)
9. 성과와 배운 점, 앞으로 개선할 점

**트러블슈팅 작성 예시** (문제 → 원인 → 해결 → 결과 수치)

> 문제: 코스 추천 API 응답이 평균 2.4초로 느림. 원인: 기상청과 에어코리아 API를 매번 순서대로 호출. 해결: `asyncio.gather`로 병렬 호출하고 Redis로 1시간 캐싱. 결과: 평균 응답 2.4초에서 180ms로 단축.

(위 수치는 작성 형식을 보여주는 예시이며, 실제 측정값으로 바꿔 쓴다.)

**예상 트러블슈팅 소재**

- 외부 API 캐싱으로 컨디션 조회 응답 시간 개선
- FastAPI 비동기 병렬 호출로 전체 응답 시간 단축
- Neo4j와 PostGIS + pgRouting의 경로 탐색 비교와 최종 선택 이유
- LLM이 없는 코스를 지어내지 않도록 역할을 나눈 설계
- 서로 다른 공공데이터의 좌표 체계를 통일하고 매칭한 과정

**개발 중 기록 습관**

- [ ] 막혔던 문제와 해결 과정은 그날 바로 블로그나 노션에 메모
- [ ] 개선 작업 전에 "개선 전" 수치를 꼭 측정
- [ ] 기능을 완성할 때마다 스크린샷이나 GIF 저장
- [ ] 기획서, ERD, 와이어프레임을 기획 과정 자료로 보관
- [ ] 배포 링크가 면접 기간에 살아 있는지 확인, 내려야 하면 1\~2분 시연 영상 준비
